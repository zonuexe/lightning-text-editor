# ターミナルと文字幅・Grapheme Cluster の深淵

エディタを自作していると、必ず**「全角文字や絵文字を入力したときにカーソルの位置がズレる」**という現象に遭遇します。

本プロジェクトの基本実装では、40分で作り切ることを最優先にして**簡易EAW（East Asian Width）**判定を採用していますが、ユーザーが「絵文字や結合文字を入れたら崩れたぞ！」と気づいたときは、このドキュメントの出番です。

---

## 💥 なぜズレるのか？ 3つの難関

### 難関 1: 文字列の長さ vs 画面のカラム幅
JavaScriptなどのプログラミング言語における `string.length` は「UTF-16 コードユニットの数」です。

| 文字 | `str.length` | ターミナルの見た目 | 画面幅 |
| :--- | :--- | :--- | :--- |
| `a` | 1 | `a` | 1セル |
| `あ` | 1 | `あ` | **2セル** |
| `🍣` | 2 (サロゲートペア) | `🍣` | **2セル** |
| `🇯🇵` | 4 (地域指示文字×2) | `🇯🇵` | **2セル**（または環境依存） |
| `👨‍👩‍👧‍👦` | 11 (絵文字4つ + ZWJ3つ) | `👨‍👩‍👧‍👦` | **2セル** |

文字列のインデックス（`cursorX`）をそのまま画面上の座標として使うと、全角文字を打つたびにカーソルが後ろに取り残されます。

---

## 🧩 難関 2: 書記素クラスタ（Grapheme Cluster）問題

人間にとって「1文字」に見えるものが、コンピュータ上では複数のUnicodeコードポイントの組み合わせ（結合文字列）であるケースです。

1. **結合濁点・半濁点**:
   - `か` + `\u3099`（濁点結合文字） = `か゚`
   - `Array.from("か゚").length` は `2` になってしまい、Backspaceを1回押すと濁点だけが消えて「か」が残る。
2. **異体字セレクタ（IVS）**:
   - 葛（U+845B）+ VS16（U+FE0F）
3. **絵文字の結合（ZWJ: Zero Width Joiner）**:
   - 家族絵文字 `👨‍👩‍👧‍👦` は、`👨 + ZWJ + 👩 + ZWJ + 👧 + ZWJ + 👦` の合体文字。

### 解決策（モダン言語での救世主）
JavaScript / TypeScript では、標準の **`Intl.Segmenter`** を使うことで外部ライブラリなしで書記素クラスタに正しく分割できます。

```typescript
const segmenter = new Intl.Segmenter("ja", { granularity: "grapheme" });

// 👨‍👩‍👧‍👦 も か゚ も 🇯🇵 も、人間が見た通りの「1書記素」として配列化される！
const graphemes = Array.from(segmenter.segment(text), s => s.segment);
```

## 🖥 難関 3: ターミナルエミュレータ側の解釈の不一致

これが最も深い沼です。  
プログラム側がいくら正確にUnicode仕様に従って計算しても、**「実行しているターミナルアプリ（iTerm2, macOS Terminal, Alacritty, WezTerm, VSCode内蔵ターミナル等）がその文字を何セルで描画しているか」** と食い違うとズレが発生します。

- Unicodeバージョン（Unicode 11 vs 15）による絵文字幅の違い
- 東アジアの曖昧幅（Ambiguous Width: `※`, `§`, `α` 等）の設定（1セルか2セルか）

---

## 🧭 難関 4: 東アジア曖昧幅（Ambiguous Width）と `mb_strwidth()` の結論

Unicode EAW仕様には、環境によって幅が1にも2にも揺れる **曖昧文字（Ambiguous: A）** が定義されています。
- ギリシャ・キリル文字（`α`, `β`, `γ`, `д` 等）
- 記号（`※`, `§`, `★`, `☆`, `○`, `●`, `■`, `▲`, `±`, `×`, `÷`, `℃` 等）
- 一部の矢印（`←`, `↑`, `→`, `↓` 等）

### 1. `mb_strwidth()` の特性
PHPの標準関数 `mb_strwidth()` は、**Ambiguous文字を常に「幅2」** としてカウントします。
- **端末が非EAW（Ambiguous = 1）の場合**: `※` を打つとカーソルが1セル右にズレる。
- **端末がEAW（Ambiguous = 2）の場合**: `mb_strwidth()` の計算と画面表示が100%一致し、完璧に動作する。

### 2. 端末がEAW環境かどうかを検知する手法（DSRプローブ）
端末エミュレータ（iTerm2, macOS Terminal, Alacritty 等）が現在Ambiguous文字をどちらの幅で描画しているかは、**DSR（Device Status Report: `\x1b[6n`）** を使って起動時に1度だけプローブ（問い合わせ）することで100%確実に動的検知できます。

```text
[エディタ] ──( 画面外で '※' を出力 )──► [端末]
[エディタ] ──( カーソル位置照会: \x1b[6n )──► [端末]
[エディタ] ◄──( 応答: \x1b[1;3R ] )────── [端末]
  => 列が 3（2マス進んだ）なら「EAW環境（Ambiguous=2）」と判定！
  => 列が 2（1マス進んだ）なら「非EAW環境（Ambiguous=1）」と判定！
```

### 3. 設計上の結論
1. **動的検知またはEAW環境下では**:
   PHPの `mb_strwidth()` をそのまま使うのが最もコード量が少なく、パフォーマンスも最高。
2. **プローブを行わない軽量実装では**:
   現代のターミナルのデフォルト設定（Ambiguous = 1）に合わせて、確定全角（CJK漢字・ひらがな・カタカナ等の Wide / Fullwidth）のみを幅2、Ambiguous記号は幅1とする安全側判定をデフォルトにするか、設定（`--eaw` 等）で切り替えられるようにするのが実用上のベストプラクティス。

## 🎯 本プロジェクトでのスタンス

1. **基本（40分枠内）**:
   - ひらがな・漢字の範囲を大まかにカバーする「簡易EAW」または「PHPの `mb_strwidth()`」で軽快に進め、まずは動かす快感を優先する。
2. **発展（ユーザーが気づいた時）**:
   - **Grapheme Cluster**: `Intl.Segmenter` で書記素クラスタ分割に切り替え、絵文字や結合文字の破壊を防ぐ。
   - **Ambiguous Width**: `\x1b[6n`（DSRプローブ）による端末動的検知の仕組みや、`mb_strwidth()` の特性について語り合い、Unicodeと端末の奥深さを楽しむ！
